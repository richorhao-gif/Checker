# Agent Note: 计划条在所属轮次结束后取已结束姿态

Status: implemented

[English](2026-09-06-todo-strip-settled-posture.md) | 中文

## 问题

计划条原本渲染模型最后写下的状态，并无条件地让 `in_progress` 圈旋转。`todos` 投影故意在 `turn/end` 之后保留已完成的清单，只在**下一次 `turn/start`** 才清空（[轮次限定的计划生命周期](../feature/2026-07-28-todo-plan-clears-on-next-turn.md)），因此一个再也不会有下一轮的会话，其最后一个未打勾条目会永久动画下去，而表头仍把该条目计为进行中。

这是循环本身的性质，不属于任何单个部署。轮次在模型输出文本且不带任何工具调用时结束，所以一份以「汇总结论」收尾的计划，其最后一项无法由模型自己打勾：写出报告就是写出这一轮的结束。要打勾，模型需要把 `todo_write` 捆进输出报告的那一步，然后再发一个完全不带内容的额外步骤。

标书审核部署把这个缺口从短暂变成永久，因为提交文档即封存会话并锁死编辑器（[审卷台](../architecture/2026-09-05-bid-review-reviewing-desk.md)）。一次对单份标书的封存审核显示五项中四项已完成，而「汇总审核结论」仍在旋转，表头读作「4 已完成 · 1 进行中」。在普通聊天会话中，同样的渲染只在用户阅读答案的那段时间可见，并在下一次 `turn/start` 时消失。

## 决策

dock adapter 从它作为 owner prop 已经拿到的会话快照派生一个姿态，并把它作为纯 prop 传给面板。面板保持为 props 的纯函数；派生逻辑是一个模块 `skeleton/todo-posture.ts`，不新增订阅、不新增 projection key、不改 host。

三个值，按优先级排列：

- `halted`：Host 已删除该会话。被删除的会话永远不会再有 `turn/start`，在其上继续动画就是永久动画，而把它报成已完成则是在宣称一次从未发生的完成。
- `live`：Host 报告有轮次在跑。该位是 Host 对「是否有轮次在执行」的权威，任何派生读数都不得压过它。
- `live`：已加载窗口内没有任何轮次边界，或窗口内最高那个边界只有开始没有结束。清单所属的那一轮可能正是被翻页移出窗口的那一轮；而最高边界未结束却同时 running 位已清，是掉帧或断连，重连会自行重新同步。两者都不是可以据以下结论的证据。
- `halted`：窗口内最高那一轮留下失败证据——`turn-error` 节点、`turn-max-tokens` 节点，或被中断冻结的 assistant 节点。三者都只按该轮的轮次号匹配。
- `settled`：其余情况。

渲染随姿态而定。`live` 就是本 note 之前计划条的渲染。`settled` 把每个仍未打勾的条目渲染成已完成字形，并把表头塌缩为只剩已完成计数。`halted` 保留每个条目的真实状态、让圈静止不转，并把表头进行中那一段替换为 `todo.progress.stopped`。

三种姿态下，每行的 `data-status` 都携带模型写下的状态。派生读数另行发布为面板根上的 `data-posture`，它同时也是 CSS 用来限定圈动画的选择器。

## 为什么姿态在 client 侧派生

`todos` 投影由 host 计算，并到达会话快照的每一个消费者，包括仅供自动化的 ACP 桥与 Python SDK。把一个显示层读数折进投影，等于把模型从未写过的状态交给它们每一个，并且因为改变了既有 key 的含义而需要把 `stateVersion` 从 2 升上去。

dock slot 已经供给了这些事实。`conversation.input.dock` 是会话作用域的列表 slot，其 owner share 就是整个 `ConversationSnapshot`，且其契约禁止条目自行订阅，所以 adapter 已经收到的那份快照就是它唯一可读的来源。派生返回一个原始字符串，因此不需要 memoization。

本包已经用同一标准要求过另一个活动指示器。模型重试行的 Host running 位只控制实时动画，随后该行显示静态的已完成或已取消标签。一个在没有任何东西运行时仍在动画的指示器，按本包已经写下的规则就是错的。

优先级沿用审卷台自己的 stage 派生，其首行同样把已删除的会话置于运行中的会话之上。

## 考虑过的替代方案

- **在 `turn/end` 时写入一条合成的 `todo/write`** —— 伪造一条模型从未写过的日志记录。会话日志是模型自己的证词，而[轮次限定的计划生命周期](../feature/2026-07-28-todo-plan-clears-on-next-turn.md)已为镜像形状以同一理由拒绝过：「在 turn start 追加一条空 `todo/write`——为了一条 UI 生命周期规则去改日志」。
- **在 host 的 `todos` 投影里重写状态** —— 同一件伪造下沉一层，外加一次 `stateVersion` 升级，并把一个呈现层决定泄漏给投影的每一个消费者。
- **在提示词里要求模型作答前先勾掉最后一项** —— 清单每次运行都由模型自拟，而循环的终止条件使这条指令无法达成：输出收尾文本且不带工具调用，正是结束这一轮的动作本身。
- **在所有已结束的轮次里都冻结圈但保留进行中状态** —— 这就是把 `halted` 普遍化。它什么都不伪造，但会把每一次成功的轮次都标成像是提前停下了，比被修的那个虚假更糟。该渲染保留给真正失败的轮次。
- **冻结圈但不动表头文字** —— 表头的「N 进行中」正是那个旋转的圈用文字说出的一句话，而它是屏幕阅读器用户唯一的通道。冻结其一不冻结其二，会让无障碍名称与视觉互相矛盾。
- **把 `settled` 限定为「除末尾若干进行中外其余都已完成」** —— 为一个读者感知不到的区分多加一条分支和一个测试，而且会让列表中间某个未打勾条目永久旋转。
- **把改动隔离进 `ui-bid-review`** —— 部署包可以复用既有的 `todo` id 向 `conversation.input.dock` 注册自己的计划条，从而替换那一格。代价是一个 fork 出来的展示组件连同它自己的 spec 与覆盖率文件、在活的查重门禁下重复表头计数与字形逻辑、让该缺陷对所有其他部署保持未修，并让部署包拥有一个它本来只是遮蔽的会话域关注点。缺陷不属于某个部署，修复也就不属于。

## 后果

封存会话的计划条现在读作已结束而不是正在工作；普通会话的计划条则在 `turn/end` 到下一次 `turn/start` 之间、清单仍在屏幕上时读作已结束。DOM 里没有任何东西在宣称一次模型没写过的完成：行保留模型自己的状态，派生读数挂在另一个属性上。该属性同时也是动画的 CSS 钩子，所以给转圈加门禁没有新增 class，也没有在本仓其他地方处于 100% 覆盖率体制下的组件里新增分支。

一个新文案键 `todo.progress.stopped`，两种语言各一份。`settled` 不需要新键：既有的已完成计数本身就已经是对一份已结束计划完整且真实的陈述。

部分取代 [web todo 展示](../feature/2026-07-23-web-todo-display.md)。被顶掉的只有其「TodoPanel: the durable list as a persistent strip」小节里的两个主张：状态无条件渲染对应字形，以及表头按模型原始的逐状态计数。事件溯源、两个渲染面、逐调用行钉住的字段，以及计划条的折叠行为，全部仍归该 note 所有。

部分取代[轮次限定的计划生命周期](../feature/2026-07-28-todo-plan-clears-on-next-turn.md)。`turn/end` 仍保留已完成清单可见，下一次 `turn/start` 仍清空它。该 note 的规则多出一条从句：清单在越过自己那一轮仍可见期间，按那一轮留下的样子渲染——轮次正常结束就是已完成，没有正常结束就是已停止。

多个条目可能同时未打勾，因为 `standard` 预设允许并行的 `in_progress`（[并行进行中条目](../feature/2026-07-26-todo-parallel-in-progress.md)）。这正是 `settled` 表现为塌缩成一个计数、而不是翻转单独一行的原因。

没有 `prefers-reduced-motion` 出口：轮次运行期间圈无条件动画，在系统里要求减少动态效果的用户仍会看到它。为把本次改动限定在姿态上而刻意暂缓；已记入本包 README 的已知限制。

`packages/client/ui-conversation/tests/todo-posture.client.spec.ts` 钉住派生的每一条分支，包括最高那一轮里三种失败证据各自的正例，以及三者各自来自更早一轮的反例——后者正是让这个折叠保持按轮限定的东西。`tests/todo-panel.client.spec.tsx` 钉住三种渲染、`data-status` 与 `data-posture` 的分离，以及 dock 读取自己 owner share 的路径。两者都位于本包既有的 client 通道覆盖率豁免之下，因此都不受 100% 门禁约束。

装配后的 web 快照通道不变。持有 todo 面板的那个夹具会话，其 `running` 位被钉为 true，且该 spec 从不进入 prompt 重放或取消路径，所以它派生出 `live`，渲染与改动前完全一致，其 golden 逐字节相同。queue-actions 的 golden 捕获的是一个被刻意挂住的轮次，屏幕上仍带着只在 running 时才出现的 chrome，理由相同。本 note 写就的机器上没有安装 Playwright，所以那条通道是读出来的，不是跑出来的。
