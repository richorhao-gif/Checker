# Agent Note: 标书审核的印章只读一行判定声明，并且可以判为待核验

Status: implemented

[English](2026-09-06-bid-verdict-declaration-line.md) | 中文

## 问题

审卷台的印章原本靠在意见书全文里搜「不符合」三个字来判定：搜到即判不通过，否则搜「符合」判通过（[审卷台](../architecture/2026-09-05-bid-review-reviewing-desk.md)）。子串扫描分不清一句话是结论、是被引用的招标要求、是假设句，还是自我否定。

五份真实标书的审核记录已经付出了代价。其中两份审的是同一个招标编号 ZY26-CZ06-WZ177，同一个 `.doc` 上传两次，实质结论几乎一致，印章却相反：

- 一份盖「符合」。它的正文里「不符合」一次都没出现——0 次，而「符合」出现 7 次——并且同样列出了它无法证实的那两项要求。
- 另一份盖「不符合」。它的正文里「不符合」出现 2 次，「符合」出现 12 次，而第一处就在「不是简单"不符合"，而是主体与资质符合，但有 4 项资格硬指标现有资料无法证实」里面，这句话的意思与扫描找到的那个词恰恰相反。第二处是「若这两项无法落实，判定为不符合资格」，一个假设句。

更深一层的原因是词汇，而不只是读法。两次审核卡住的是同一个事实：标书提出硬性要求——京津冀或北京的固定供货点、在北京登记的配送车辆——而公司共享资格记录既不能证实也不能否定，因为记录里只有济南登记、3200 平方米冷库与 150 公里配送半径。只给「符合」与「不符合」两个词，模型就只能靠措辞来表达「记录没有给出答案」，而印章读不懂措辞。

## 决策

判定加第三个值，读法随之改变。

[`prompt.ts`](../../../../packages/client/ui-bid-review/src/client/prompt.ts) 新增 `BID_REVIEW_VERDICT_CONTRACT`，是提交在固定问题之后的第二段固定文案。它要求意见书第一行必须恰好是 `判定：符合`、`判定：不符合` 或 `判定：待核验`，冒号后不得再加任何字词，并给出三者的取舍规则：招标要求中的硬性条件，凡公司资格记录既不能证实也不能否定的，一律判「待核验」并逐条列出缺少哪些资料、由谁出具，而不得因为推测可能有就写「符合」，也不得因为查不到就写「不符合」。同一次编辑把固定问题里的「不符合给出出原因」中重复的「出」删掉。

`verdictOf` 只读这一行声明，别的都不读。它取正文前八行，剥掉 `*` 与反引号以便被强调符包裹的声明仍能读到，然后匹配 `/判定[：:]\s*(不符合|待核验|符合)/`——两种冒号宽度都认，因为一行中途换了输入法的模型仍然是声明了的。第一个命中决定结果；头部什么都不匹配就让印章不落结论。八行是给标题与引用块留的余量，契约要求声明写在第一行。

剥除只作用于读取。声明行保留在渲染出的正文里、在复制的文本里、在下载的文件里，因为它是模型自己的话，也是印章所依据的证据。

`DeskVerdict` 现在是 `reject | pass | unverified | none`，并新增一个推导 `sealInk` 把判定映射成墨色：通过用墨绿，待核验用琥珀，不通过与未落结论用朱红。琥珀已经是审卷台表示「在等人」的颜色——暂停注记与页边线都用它——而一件待核验的事实等的正是有人去补资料。`ReviewDesk` 在一张模块内私有的 CSS 类映射表里查出该类名交给印章，因此组件没有为判定增加任何分支。双语文案各新增一个键 `desk.seal.unverified`。

五份既有记录都没有判定声明行，因此五份现在都盖未落结论的印章。这是决定，不是遗漏：为它们保留旧的全文扫字做兜底，就等于保留造出这对矛盾印章的那个读法；要在旧审核上看到真章，就得重新送审一次。

## 为什么印章只读一行而不读全文

审卷台一贯的规则是：页面上只出现日志自己承载的东西，不编造。全文扫描破坏这条规则的位置在读取一侧而不在渲染一侧——它输出一个意见书从未给出的结论，取自意见书用于别处的那个词。只读 prompt 要求模型自己写下的那一行，使印章保持为一次转录；它也让失败变得诚实——模型没有声明时，印章就直说没有声明，而不是猜一个，这与审卷台不显示任何无人测量的标书业务进度是同一个理由。

限制在头部才让这条限制真正成立。没有限制，正文里任何形状像声明的短语都能决定结果，而造出本注记的那两个句子——一句自我否定与一个假设句——仍然会命中。

## 考虑过的替代方案

- **保留全文扫字，作为没有判定声明行时的兜底**——否决。它保留了那个对同一份标书的相同发现盖出相反印章的读法，因此五份既有记录的矛盾照旧，将来任何漏写声明行的意见书又会被猜一次。
- **让审卷台自己从正文推断判定**——否决。把 12 次「符合」与 2 次「不符合」衡量一遍、或判断哪一句才是结论，都是在编一个模型没有给出的结论。这与审卷台在进度上拒绝的编造是同一种，而且它要求读懂中文行文，而不是读一行。
- **只加「待核验」文案，读法照旧扫全文**——否决。措辞飘移原封不动：模型仍会把一件没有定论的事实写成相邻两值之一再加一段含糊话，扫描仍会盖出正文里最先出现的那个词。
- **在 Host 侧解析判定并发布为 Session 事件**——本次否决。`dsh-bid-review` 不组装 prompt、不拥有输出契约，因此 Host 也得拿到契约，而一个 `SessionEventMap` 成员对所有构建都是必须可读的。声明行已经持久存在于审卷台读取的那条 assistant 消息里，事件只会为一行文字已经说明的事实再存一份。如果将来有判定需要送到不渲染意见书的消费方，这仍是正当路线。
- **读到之后把声明行从正文里剥掉**——否决。审卷台会因此渲染出一份与日志不同的意见书，导出的公文也会失去它自己印章所依据的那句话。印章把那一行重复一次是更便宜的代价。
- **把匹配锚定在第一行**——否决。契约要求第一行，但把标题或引用块写在声明之上的模型仍然是声明了的，拒读这种写法会让一份已经给出结论的意见书盖着未落结论的印章。八行容得下一个标题，也够不到正文里的假设句。

## 后果

印章现在说明三种结论与一种拒绝，而拒绝是对一份没有声明的意见书的诚实读法。契约存在之前记录的每一次审核都盖拒绝，因此本部署那五个会话的印章变了，正文一个字没动。

契约是一条关于模型行为的主张，没有任何单元测试能证明它。`desk.ts` 的 spec 钉住读法，`prompt.ts` 的 spec 逐字钉住两段文案，二者都不能说明模型是否遵守；那要在浏览器里对着五份既有记录与一次新送审验证，而新送审消耗一次真实模型调用。

新增一个文案键与一个 CSS 类 `.sealHold`。它不能复用审卷台已有的 `.amber`，因为那个名字是 `dotTone` 返回的状态点色调并被直接当类名使用，所以印章需要自己的类名。

部分取代[审卷台](../architecture/2026-09-05-bid-review-reviewing-desk.md)。它有两处主张被替换：`verdictOf` 从收尾文本里先搜「不符合」再搜「符合」来读出印章，以及未落结论的印章属于「既未说符合也未说不符合的报告」。它的原则——审卷台不说明模型没有给出的结论——保留下来，而判定声明行正是现在执行这条原则的机制。遮蔽注册、派生姿态、替身纸面、页眉与依据的读取、铅笔操作都不变。

[固定问题界面](../architecture/2026-09-04-bid-review-fixed-prompt-surface.md)关于「固定问题是 `prompt.ts` 里的字面产品文案而非词典条目」的主张不变。输出契约按同一条规则加入，也带着同一条局限：二者都不可本地化，因为它们都以用户消息提交给模型。
